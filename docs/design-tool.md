## Problem statement

The tool grew by accretion while Noah seeded two events (Crescendo of Night 3 Ep 0 on 2026-10-13
and 14, Eclipse 1st Cour MBAACC on 2026-10-16). It works, but it works with Noah and Claude at the
keyboard. "Realer" was ruled in this session as: **reliable and complete for Noah's own seeding
first, shareable with other TOs second**, and above all **intentional**: the next version is
designed on purpose, with a stated job, instead of being the sum of what got asked for on seeding
day.

What the evidence says the tool has and hasn't done (as of 2026-10-28):

| | |
|---|---|
| Events seeded with it | 3 (UNI2 5 players, MBTL 22 to 24, MBAACC 182) |
| Rows in `registry/tiers.csv` (all MBAACC) | 712 |
| Tiers set in the app | 107 |
| Justifications written | 0 of 107 |
| Seeds typed into start.gg by hand at Eclipse | 182, one at a time |
| Pull plus W-L for Eclipse, all games | about 90 minutes |

The zero justifications are not a failure of the field. Noah: *"not needing elaboration. results
speak for themselves. notes are for clarifying details. they help me remind myself of what results
don't clearly tell me."* The build misread "justification" as a sentence; the justification is the
results as they stood when the tier was set.

## What makes this cool

Open a tournament page. Every game you're seeding is a tab. Every player you've ever reviewed
already has a tier, colored by how recently you looked at them, with the tournament you looked at
them in on hover. Each game's majors column shows only that game. The schedule tab shows every
player's blocks across all the tournament's events. Nothing was pulled twice. And when the tiers are
set, the optional last step puts them into start.gg's seeding in one confirmed click instead of 182
keystrokes.

## Noah's workflow, in his words (the thing the tool serves)

- **Profiling:** *"looking over results, profiling a player, assigning a tier."*
- **Seeding:** *"arranging players, adjusting tiers, looking at data for tie-breakers to compare
  players who may be close."*
- **Handoff to start.gg:** *"the tiers let me have a good starting point in start.gg: I put each
  assigned tier in start.gg's seed generator. all 10s above all 9s above all 8s etc when the
  generator runs. then I can move in start.gg as needed based on schedule conflicts and more."*
- **Stale tiers:** *"a tier going stale means it didn't align with where I tiered others with
  similar results. this doesn't need to be baked into the tool because it is inherently somewhat
  related to gut feeling."*
- **Scope line:** *"don't overcomplicate it. it's 3 tables, and clicking a page for seeding an event
  shows a slice of data."*

## Constraints

1. Local, Node 24 built-ins only, no hosting, no auth. Token in `.env`, never in code or output.
2. start.gg budget: 80 requests/min and a separate server-time budget ("over the threshold for
   recent request time"). **One limiter, one queue, one request in flight** for everything the app
   does against start.gg: pool pull, W-L, schedule pull, seed push. 90 s waits on the time-budget
   error. W-L costs about one set lookup per result.
3. Noah's standing rule: no AI on FGC-facing surfaces. Claude in the private workflow is fine.
   Matters for the share phase, not this one.
4. Binding display rules from `docs/usage-log.md` stand: (1) per result event name, placement out of
   entrants, W-L, date secondary; (2) no aggregate counts; (3) every series as best placement (with
   W-L), best W-L, average W-L; (4) tables, not bullets.
5. Next event: week of 2026-11-02. Noah: *"deadline shouldn't be relevant"*. It's context for the
   build order, not a driver of scope.
6. Build process: personal-staff Engineering team, owner and auditor passes. Two prior audit
   defects came from out-of-band edits drifting. See standing rules under Rulings.
7. Seeded events are **singles**. The add-tournament picker hides teams events. (Doubles and 2v2
   have no `player_id` to `seedId` mapping and are out of scope.)

## Premises (agreed 2026-10-28, with Noah's two revisions)

1. **The tool's job** is profiling and tier upkeep per game. **It ends at tiers.** Getting them into
   start.gg is optional and has two forms: push by API, or an exported list. Ordering is tiered by
   default (within-tier order left as start.gg already has it); strict ordering is an option by
   dragging rows. The tool never asserts a full order beyond tiers unless Noah dragged one.
   Arranging, conflict fixing, and judging staleness stay with Noah.
2. **Three tables, nothing else saved.** Tiers per game, persistent, carrying the date and tournament
   of last review. A player-and-results pool per tournament, kept for the life of the tournament.
   Schedule blocks per player per date, per tournament.
3. **Results are banked for the life of the tournament:** kept until Noah cleans up or deletes the
   tournament, which he can do once it is done. Before cleanup, an optional archive keeps the final
   standings so the seeding can be reviewed against how it ended. Nothing about results is kept long
   term, because it stales. Pulled once per tournament and shared across its events. The 2-year
   window is the primary body; older results matter only when recent volume is thin.
4. **The results are the justification.** No reason field. Notes stay, for what results can't show.
5. **Majors are per game.** A known-major column exists only where the seeded game was a main event
   at that tournament, and shows only that game's result. Game-specific majors are a per-game config
   list. Everything else in the seeded game stays as series. Other games stay in one column, grouped
   by game.
6. **One page per tournament,** a tab per game being seeded plus a schedule tab, each a slice of the
   same pool.
7. **The Seeded ✓ is the review mark.** It writes last-reviewed to the tiers table and stops being
   browser state.
8. **Seeds can go to start.gg by API** (mutation verified in start.gg's docs, see Landscape; Noah's
   token not yet tried), replacing the typed step. Optional.
9. **Sharing is a later phase.** This version avoids choices that would block it (hard-coding
   MBAACC, the token's location, a Windows-only launcher) but builds nothing for it.
10. **Simple means local.** As today.

## Data model: the three tables

### T1. Tiers (persistent, per game). `registry/tiers.csv`

Noah's database. Sheets-portable CSV, one row per (game, player). Changes from today's file:
drop `justification` (0 values, so lossless), add the two last-reviewed columns.

| column | filled by | meaning |
|---|---|---|
| `game_id`, `game_name` | pull | the game the tier is for |
| `player_id` | pull, when linked | start.gg `Player.id`, the join key. Blank for sheet-only rows until a pull links them by tag. |
| `startgg_tag`, `sheet_tag` | pull / sheet import | as today |
| `tier` | Noah | integer. Higher is stronger. Tier 0 exists (97 rows); its meaning is an open question. |
| `notes` | Noah | what results can't show |
| `decided_on` | app | date the tier last changed |
| `last_reviewed_on` | app, via ✓ | **new.** date Noah last looked at this player with intent, whether or not the tier moved |
| `last_reviewed_tournament` | app, via ✓ | **new.** tournament slug where that review happened |
| `source` | app / import | as today |
| `sheet_region`, `sheet_placements`, `sheet_notes` | sheet import | carried over, read-only |

Rules:

- **✓ semantics.** Clicking ✓ sets `last_reviewed_on` to today and `last_reviewed_tournament` to
  this tournament. Clicking it again (un-✓) is an undo for a misclick only: it clears both fields
  if `last_reviewed_tournament` equals this tournament **and** `last_reviewed_on` is today;
  otherwise it does nothing. A review recorded earlier is never destroyed by a click. The row is
  shown as reviewed (green) when `last_reviewed_tournament` equals the page's tournament.
- **Backfill at migration.** Eclipse's ✓ marks lived in one browser's storage and are lost. For
  rows with `source = app` and `decided_on` set (107 rows), the migration sets
  `last_reviewed_on = decided_on` and `last_reviewed_tournament = eclipse-1st-cour`. Tested against
  the real file's shape.
- **Display.** The Tier cell takes a recency color from `last_reviewed_on` measured from today
  (bands under Open questions); hover shows `last_reviewed_on` and `last_reviewed_tournament`. The
  in-place editor edits `tier` and `notes` only. No reason prompt.
- **File shape.** UTF-8 with BOM, every field quoted, as today; the writer keeps emitting the BOM so
  Sheets import keeps working.

### T2. Player pool with results (temporary, per tournament). `out/<tournament-slug>/`

One pull per tournament, not per event. The union of registrants across the seeded events, each with
every result in the window, all games, plus the shared W-L cache.

| file | contents |
|---|---|
| `players.csv` | one row per registrant of any seeded event; today's columns plus `events` (which seeded events they entered, by event slug) |
| `results.csv` | as today, one row per player per past event, all games. `is_event_game` is **dropped**: it's meaningless in a multi-game pool; each tab computes `game_id === tab.game_id`. |
| `set-records.json` | W-L cache keyed `<player_id>:<event_id>`, shared by every tab |
| `meta.json` | **written by the pull only:** tournament (slug, name, `startAt`, timezone), its seeded events (slug, name, game, `startAt`, phases), `run_at`, window, counts, failed players |
| `state.json` | **never written by the pull:** the seeded-event set Noah ticked, linked side tournaments (today `conflicts/linked.json`), lifecycle overrides `marked_done` and `archived`, and `pushes` (one entry per seed push: event, time, seed count) |
| `standings.json` | optional archive: final placement per entrant per seeded event |
| `schedule.json` | T3, below |
| `current` | one line naming the live pull directory (see the swap rule) |

Rules:

- **Refresh writes beside, then swaps the directory.** A pull writes `players.csv`, `results.csv`,
  `meta.json` and its own `_work/` into `out/<t>/pull-<stamp>/`. When every player is complete,
  limited or failed, the tool writes the new directory's name into `out/<t>/current` (one small file,
  written atomically) and deletes the previous pull directory. The page reads whatever `current`
  names, so it never sees a new `players.csv` next to an old `results.csv`, and a crash mid-pull
  leaves the old pull live and the new one resumable from its own `_work/`. `set-records.json`
  (W-L), `state.json`, `standings.json` and `schedule.json` live at `out/<t>/`, outside any pull
  directory, so no swap touches them. W-L fetch for missing results runs after the swap,
  summary-first where "summary" is the union of summary columns across all tabs; the page shows
  what's fetched so far on reload.
- **Refresh means everything.** The header Refresh re-pulls registrants of every seeded event and
  every player's results (new results since the last pull are the point). The W-L cache carries,
  keyed by event id, so only new results cost set lookups. **Ticking a new event is incremental:**
  it pulls only the players not yet in the pool.
- **Before the first pool exists** the tournament page shows the event picker and a Pull button with
  status; no tabs.
- **Changing the seeded-event set.** The set lives in `state.json`. Ticking a new event triggers the
  incremental pull above. Unticking hides the tab; the event stops counting as seeded for status and
  for `players.csv.events`, and the next full Refresh drops players who are in no seeded event.
- **Status is computed at read time**, not stored: `live` until the latest `startAt` among the
  currently ticked events has passed, then `done`; `marked_done` and `archived` in `state.json`
  override.

### T3. Schedule blocks (temporary, per tournament). `out/<tournament-slug>/schedule.json`

Already built as `conflicts/` (uncommitted): every player's events, pool (block) and wave start per
date, including linked side tournaments (today `conflicts/linked.json`, moving into `state.json`).
Moves next to the pool it belongs to and joins the single request queue (constraint 2); today it
runs as a separate job. Visibility only: it never fixes a conflict. Noah: *"automatic
fixes/suggestions can come later because this is nuanced and can be affected by things unseen such
as someone arriving at an event late or leaving early."* Side-event blocks: linked by start.gg page
when one exists, with no guarantee the lettered blocks match; noted by hand with a time otherwise.

## Pages

- `GET /` lists tournaments: live first, then done, then archived. **Add a tournament:** paste a
  tournament URL or any of its event URLs; the tool makes one synchronous start.gg request for the
  tournament's events (name, game, `startAt`, teams or singles, phases) and shows a picker; Noah
  ticks the singles events to seed; Pull starts the job.
- `GET /t/<tournament-slug>` is **the page**. Tabs: one per seeded game (the seeding table, as
  today, sliced to that game), one **Schedule** tab (today's conflicts page), and a header with
  Refresh, status, and the lifecycle controls. Stable URL; reload shows the latest data.
- The seeding tab keeps everything increment 2 built: Seeded ✓ (now writing T1), Team | Player |
  Region | Tier frozen, majors, shared series, Other series (this game), Other games, Notes, in-place
  edit, sort, compare up to 3, pin, freeze, jump-to, Needs tier only, Show team, Sheets export.
- `GET /e/<t>/<e>` redirects to `/t/<t>` with that game's tab selected **when `out/<t>/` exists**;
  otherwise 404 with a link to add the tournament. Old `out/<t>__<e>__<stamp>/` run folders and
  `conflicts/out/` are left alone and not read; Noah deletes them when he likes.

## Display rules added this session (binding)

Numbered to extend the four ratified rules.

5. **A known-major column** (CEO, Evo, Combo Breaker, Frosty Faustings; the list is per-game config)
   appears only if the seeded game was a **main event** at that tournament, not a side, community,
   2v2 or "Pre-" bracket, and shows only the seeded game's result there. Majors columns show one
   result per year; this is the existing, deliberate exception to rule 3 (a major is a single yearly
   event, not a series).
6. **Game-specific majors** (for MBAACC: Climax of Night, Eclipse) get the same column treatment.
   **One config list per game** holds both kinds: each entry a name pattern and a kind (`known` or
   `game`), so the code reads one file. Noah's rule for adding one: a series
   of the seeded game whose field is at least as large as a known major's field for that game, which
   *"means it's a main event or a big-enough one for that game."* The rule is how Noah decides; the
   config is what the code reads.
7. **Everything else in the seeded game** stays as series in rule 3's shape (shared series columns,
   then Other series).
8. **Other games** stay in one column, grouped by game, as today.
9. **Tier recency** is shown as a color on the Tier cell with the date and tournament on hover.

These rules change `lib/view/model.js` (today's `MAJORS` regex list, main-bracket = largest field,
and `is_event_game` slicing all live there), not just the data layer.

## Lifecycle

| state | how | what it means |
|---|---|---|
| live | computed: latest seeded event's `startAt` not yet passed | Refresh available |
| done | computed when it has passed, or `marked_done` | Nothing is blocked: Refresh, tier edits, ✓, export and push all stay available (late registrations and a multi-day tournament's later tabs are normal). Done only changes the `/` ordering and surfaces Archive and Delete. |
| archived | `archived` set by the Archive control | `standings.json` fetched (final placement per entrant per seeded event); pool still present until deleted |

Controls on the page header: **Mark done** (override), **Archive standings** (on request, one
fetch per seeded event), **Delete tournament data** (removes `out/<t>/` entirely, with confirm).
T1 outlives everything; deleting a tournament never touches it.

## Outputs (optional, after tiers)

Two forms of the same list, both from a seeded game's tab:

1. **Export list:** the tab's players as CSV (tier, tag, player_id, proposed seed), numbered by
   tier with the **table's current order** within a tier. No start.gg request; works without admin.
2. **Push to start.gg:** `updatePhaseSeeding(phaseId, seedMapping)`, numbered as below with
   start.gg's current order within a tier.

**Seed numbering, both forms: higher tier gets the lower seed number**, one sequence, contiguous
1..N. A dragged strict order overrides the within-tier order.

Push mechanics:

- Target phase: the event's first phase by `phaseOrder`, named in the dry run.
- The tool queries the phase's seeds (`id`, `seedNum`, `entrant.participants.player.id`), 2 to 3
  requests for 182 entrants, and maps each seed's `player_id` to T1 and to the pool.
- **The sequence.** Every seed in the phase is placed in exactly one group, and the groups are
  concatenated and numbered 1..N: (a) seeds with a T1 tier for this game, tier descending, start.gg's
  current order within a tier, whether or not the player is in the pool (a late registrant with a T1
  row is tiered, not demoted); (b) seeds whose player has no T1 tier, start.gg's current order;
  (c) unmappable seeds (placeholder or no-player entrants), start.gg's current order. Pool players
  who are no longer in start.gg are ignored. Seeds in (a) or (b) that are not in the pool are marked
  in the dry run, which suggests a Refresh.
- **Dry run first, always.** The page shows the diff, current seed to proposed seed, grouped as
  above. Any proposed move that crosses a tier boundary relative to start.gg's current order is
  flagged, so a conflict fix Noah made by hand in start.gg is visible before a re-push reverts it.
  Posting requires a click on the dry run.
- Each push is recorded in `state.json.pushes`.
- Failure modes shown as a status line, no retry: bracket already started or phase locked, token
  not an admin of the tournament, rate limit (queued like everything else).

## Landscape (verified 2026-10-28 via Exa)

- start.gg's API has `updatePhaseSeeding(phaseId: ID!, seedMapping: [UpdatePhaseSeedInfo]!, options)`,
  with an end-to-end example that reads seeds from a sheet and posts them. Requires an admin's
  token. Source: <https://developer.start.gg/docs/e2e/update-phase-seeding/>. Verified in docs only;
  Noah's token has not run it. The first live run is a dry run against a test or past tournament.
- The same schema has `resolveScheduleConflicts(tournamentId, options)`, start.gg's own swap
  algorithm that stays within tiers. Source: <https://smashgg-schema.netlify.app/reference/mutation.doc>.
  This is the "auto-fix later" Noah deferred: one call when wanted, out of scope now.
- start.gg's Genesis 6 writeup (2019) describes exactly Noah's workflow: experts tier players,
  tiers become seed numbers (randomized within tier), a script posts them, conflicts resolved after.
  Source: <https://blog.start.gg/seeding-genesis-6-via-api-b3a75c936dcb>.
- Nothing found that does this job. Closest: Ausmash Auto Seeder (SSBU, Australia; import, reseed to
  avoid recent opponents, upload) <https://seeding.ausmash.com.au/>; Braacket (seeds from its own
  league rankings) <https://braacket.com/>; kusa-data (Melee analytics) <https://github.com/McCune1224/kusa-data>.
  None pulls every registrant's cross-game history into a per-game table with the TO's own tiers
  persisted. Conventional wisdom is sound here; this builds on it.

## Approaches considered

### Approach A: three tables as files inside the current app (chosen)
Summary: keep `lib/view/render.js` and the page's front end; change the pull's output layout
(`lib/run.js`, `lib/output.js`), the data layer (`lib/view/data.js`), the slicing and majors logic
in `lib/view/model.js`, the refresh job (`app/jobs.js`), the routes (`app/server.js`) and the tiers
writer; add the tournament page shell with tabs; fold `conflicts/` in as the schedule tab and T3.
Effort: M (human about a week / CC a few owner-auditor passes). Risk: Med. The one-run-folder-per-
event convention is assumed across the pull and the app.
Pros: the rendering and most of the view logic survive; `tiers.csv` stays Sheets-portable; each
step is usable on its own. Cons: lifecycle and cleanup are hand-rolled file conventions.

### Approach B: three tables in a local store (`node:sqlite`), pull and app decoupled through it
Effort: L (human 2 to 3 weeks / CC 1 to 2 days of passes). Risk: Med.
Pros: lifecycle, archive, slices and the W-L cache become queries; one file is the whole state, the
cleanest base for a second TO. Cons: rewrites the pull's output layer and every reader before the
next event; replaces audited code.

### Approach C: tiers live in Google Sheets, the app shows results only
Effort: S. Risk: Low for the build, high for the workflow.
Pros: smallest build; Noah already manages and shares tiers in Sheets. Cons: breaks the loop Noah
described: the ✓ can't write last-reviewed, and tier edits leave the page where the evidence is.

## Recommended approach

**A.** Noah's ruling: *"files in current tool."* It matches *"don't overcomplicate it"*, the pure
logic already lives in modules, and the restructure is the data layer, the pull's output layout and
the page shell. B stays the shape to reach for in the share phase if file conventions get in the way.

Noah also noted: *"I've really liked the experience of building a Tauri app for simple tools like
this. easy to use and no need to maintain a deployment."* Recorded as the **share-phase direction,
non-binding on this increment:** a desktop shell around this app, which the front end (plain
HTML/CSS/JS, no build) and a thin server already suit.

## Reviewer Concerns (cold review, 2026-10-28; Noah to rule)

Two rounds. Round 1 scored the first draft 6/10 (done-by-date on multi-day tournaments, the Eclipse
backfill, refresh-while-reading, push edge cases, config vs computed majors, the `model.js` blast
radius, one request queue). Round 2 scored the revision 8/10 and found seven internal
contradictions, all fixed in this text: the pull directory is swapped via a `current` pointer
instead of per-file renames; lifecycle and push state moved to `state.json`, which the pull never
writes; the push sequence is one numbered list; done blocks nothing; un-✓ is a same-day undo only;
the CSV export uses table order and needs no start.gg request; one majors config per game. Three of
round 1's scope cuts contradict things Noah asked for in this session, so they are recorded here
instead of applied:

1. **Drag-to-order (strict ordering).** Reviewer: new UI machinery for a case Noah's own words put
   in start.gg; cut it, tiered push only. Noah's ruling in session: *"tiered/unordered and strict
   ordering are options but that's easy to handle if players are draggable."* **Kept as an option;
   builds last** (step 6), and only if Noah still wants it then.
2. **Standings archive.** Reviewer: its purpose (review seeding against results) is staleness
   judgment, which the Rulings table puts out of scope; defer. Noah's ruling in session: *"it should
   be an option to archive the end results of a tournament past its date to review how the result
   ended up."* **Kept, on request only** (step 5).
3. **Tauri as a design constraint.** Reviewer: non-binding with no test and a real cost. **Agreed:
   marked non-binding** under Recommended approach.

## Success criteria (the next event, week of 2026-11-02)

- One pull for the tournament; every seeded game's tab reads from it; no result fetched twice.
- Each game's tab shows majors for that game only; no duplicate Frosty Faustings rows for other games.
- Every player tiered in the app at Eclipse shows a tier with a recency color and `eclipse-1st-cour`
  on hover (via the migration backfill).
- Clicking ✓ in one browser shows as reviewed in another.
- Tiers reach start.gg without typing: a dry-run diff, then either the posted seeding or the exported
  CSV.
- The schedule is a tab on the same page as the seeding.
- After the event, the tournament reads as done, can be deleted, and `tiers.csv` is unchanged by that.

## Distribution plan

Local, as today: `npm start` or `app.cmd`. No pipeline. Share phase (later): a Tauri shell, a
setup path that doesn't assume Windows, and per-game major lists as config.

**Amendment, 2026-11-06 (Noah: "A friend is using this now... They should be able to easily install
updates. On the main page we need a button to check for updates").** The share phase has started: the
Tauri shell ships as a Windows installer from GitHub Releases. Two rules follow, and the README's
*Desktop app* section has the details and the human steps:

- **User data never lives where the installer writes.** An installed copy keeps `registry/tiers.csv`,
  `out/` and `.env` in `%LOCALAPPDATA%\net.enpicie.seeding-ops` (lib/data-dir.js); the installer ships
  only `registry/tiers.template.csv`, from which an empty table is seeded when there is none. The first
  launch moves an older install's data out of the install folder. Checkouts and the portable ZIP are
  unchanged.
- **Updates are versioned and signed.** Every release is `v<version>` and carries `latest.json` and the
  installer's minisign signature (Tauri's updater format). The home page's *Check for updates* verifies
  the signature against `config/updater.json`'s public key before running the installer. The client is

### A2.2 Sharing one game's tiers

Noah: *"I should be able to share my tiers with respect to a game with another organizer."* Rulings:
export picks a game and gives a shareable file; import is a **review step** (new players, plus
conflicts side by side, picked per row or with "keep all mine" / "take all theirs", then applied);
an import for game X never touches game Y's rows; provenance goes in `source`; files for a different
game, malformed files, BOM and quoting are handled as the CSV upload handles them.

Decisions:

- **What is shareable.** The file carries `game_id`, `game_name`, `player_id`, `discriminator`,
  `startgg_tag`, `sheet_tag`, `tier`: what a receiver needs to match a player (id, discriminator, two
  tag forms) and read the tier. **Private, never exported:** `notes`, `decided_on`,
  `last_reviewed_on`, `last_reviewed_tournament`, `source`, `sheet_region`, `sheet_placements`,
  `sheet_notes` (Noah's own judgment trail and his sheet's annotations). Only rows with a tier are
  exported, tier descending then tag.
- **File shape.** T1's own writer (UTF-8 with a BOM, every field quoted, CRLF), so the file is a
  `tiers.csv` subset and opens in Sheets the same way. No formula guard (as T1; A2-6 stays open).
  Name: `tiers-<game>-<date>.csv`.
- **Where.** The home page, a **Tiers** section with a game picker (games in the tiers file with their
  tiered count, then the other known games), **Export tiers…** and **Import tiers…**. Tiers outlive
  tournaments (T1), so sharing is not a tournament-page control.
- **Reading a file.** `lib/upload.js` `csvRecords` (RFC 4180, CRLF / LF / CR, BOM dropped, an
  unterminated quote reported at its line). A header row is required; columns are found by name in any
  order and case, so the full `registry/tiers.csv` (anyone's) imports too, its private columns ignored.
  It must name `game_id`, `tier` and one of the four identity columns, else "not a tiers file". Rows
  for other games are counted and listed, never judged or touched; a file with no row for the picked
  game is refused, naming the games it has. A row is **unreadable** (listed with its line) when its
  tier is not a whole number 0..20, its `player_id` is not digits, its discriminator is not a start.gg
  code (bare, `user/<code>` or a profile link are accepted), or it has nothing to match by. A row with
  no tier is skipped and counted.
- **The review.** Each file row is matched to this game's rows: by `player_id`, then by
  `discriminator` (unless that row names another player), then **by tag against every row here,
  linked by an id or not** (build D pass 2, auditor finding 4: in pass 1 the tag step looked only at
  unlinked rows, as T1's own matcher does, so a file row with only a tag for a player Noah had linked
  by id read as new, and the default Apply added a hidden tag-only duplicate of him). A tag match is
  left out when the file row's own `player_id` or discriminator differs from the row's (someone
  else); one remaining row is the match, two or more are ambiguous. So a player who already has a row
  here is never added again by tag. Categories:
  **new** (no tier here: no row, or a row with no tier); **conflict** (a different tier here, shown
  side by side with the match method and Noah's own note on hover; a tag match is marked "check");
  **same** (counted); **repeated** (two file rows on one row here, at least one by an id: the same
  start.gg player, the first id match is used); **ambiguous** (one tag naming two or more rows here,
  or two file rows on one row here by tag only, A6-1's one-tag-two-people: never applied).
  Defaults: a new row is added, a conflict keeps Noah's. Per-row picks; the bulk buttons are **per
  section**: *Keep all mine* / *Take all theirs* for conflicts, *Add all* / *Add none* for new players
  (a "keep mine" has no meaning for a player Noah has no tier for, so one global pair would be
  ambiguous for new rows).
- **Apply.** The review is recomputed from the same file and the current table and must match the one
  reviewed (a fingerprint of the file and this game's rows); otherwise 409 and the page shows the
  fresh review. Then, in one atomic write and only in the picked game: an added row gets the file's ids,
  tags and tier; a taken conflict or a filled row changes `tier`, sets `decided_on` to today (the day
  the tier changed here), and fills an id the row lacks (never replaces one). Every applied row's
  `source` becomes `import <YYYY-MM-DD> from <file name>`: the provenance, shown in the grey
  "never reviewed" hover. `notes`, reviews and the sheet columns are never touched; an import is not a
  review, so it sets no `last_reviewed_*`. A taken row that was matched by tag only is listed after
  the apply for Noah to check (its ids are now written in, as an edit would).
- **Limit.** The import routes read a request of up to 2 MB (`TIERS_BODY_MAX` in `app/server.js`, the
  cap main's export POST uses), not the default 200 KB: the whole file travels as a JSON string, and
  escaping adds up to ~30% (auditor finding 8). The server writes the cap into the page
  (`data-max-bytes`), and the page measures the request it would send (UTF-8 bytes of the JSON, plus
  room for Apply's picks) against it before sending, with a message naming both sizes.
- **An unreadable table** (main's `readTiersText`: only a missing file means "no tiers"; a file held
  open elsewhere throws): the import's review and apply and the export answer 503 with that message,
  so nothing is applied over a table that could not be read (auditor finding 2), and the home page's
  Tiers section says so, lists no "(none yet)" counts, and turns Export and Import off.

### A2.3 Seeds you arrange

Noah: *"The main view should have a seed associated with players, such that when the sheet initially
loads sorted by tier, the seeds are also there in ascending order (top tier of an event is seed 1). Rows
should be draggable, so rather than just tiers a user can arrange actual seeds and sort the sheet by
seeds."* Rulings: the dragged order is the source of truth for the push; tiers only set the initial
order; the order is saved per event across reloads, with a "reset to tier order"; newcomers slot in by
tier and removed players close the gap; keep the existing within-tier tie-break; a sort-by-seed option;
the Seed column shown; keyboard reordering; show clearly whether the push uses a hand-arranged order or
pure tier order. Added the same day (relayed): **rows stay draggable right up to the push**: nothing
before the push locks, freezes or snapshots the order; the push reads the order at the moment Push is
clicked, a drag one second earlier included, never a debounced or unsaved copy; a confirm or preview
step either keeps rows draggable or re-reads on confirm; after a push the rows are still draggable and
a re-push works.

**Ruling, 2026-11-07 (build D pass 2):** Noah: *"push should prepare the seed column and then send
what was finalized."* The Seed column is always the push's source of truth, in tier order as well as
arranged: the dry run prepares the column (tier order on first load, or the saved arrangement), Noah
adjusts it by dragging, and Post sends exactly the column as it stands at the click; the dry run shows
that same sequence. This replaces pass 1's tier-mode default (start.gg's order within a tier), which is
dropped.

Decisions:

- **Two modes per event** (`lib/view/model.js` `seedOrder`). *Tier order* (nothing arranged): the
  event's entrants by tier descending, untiered last, then by tag, the table's existing tie-break
  (`orderPlayers` now calls the same comparator), recomputed on every read, so a tier edit moves the
  seed. *Arranged*: the order Noah dragged, saved in `out/<t>/state.json` as
  `seeding: { <event slug>: { order: [player id] | null, at, rev, by, seq } }` (never written by the
  pull, gone with the tournament; `order` null is tier order; `rev`, `by`, `seq` are the write rules
  below). Seeds are 1..N over the event's entrants; a tab player who did not enter the column's
  event has no seed. "Reset to tier order" deletes the event's entry (it asks first: an arrangement
  is work).
- **Reconciling** (`reconcileOrder`, used by the page, the export and the push alike): ids no longer
  entered are dropped, so the gap closes; each newcomer, in tier order among themselves, goes right
  after the **last** player in the order whose tier is at least its own (untiered: at the end; nobody
  that high: at the top). "Last", not "first below": a newcomer joins the bottom of its tier band even
  when Noah dragged a lower tier above it.
- **The push** (`lib/view/model.js` `pushPlan`). The proposed order is the Seed column, in both modes,
  reconciled with start.gg's seeds (a seed whose player is not in the column, not in the pool yet,
  slots in by its T1 tier; a column player start.gg no longer seeds is skipped), then the unmappable
  seeds. The page sends its column (both modes) with the dry run and the post; a request without one
  (a script, a test) gets the column the server computes the same way (`lib/seeding.js`
  `columnOrder`). Start.gg's own order matters only for an exact tie of tier and tag among seeds that
  are not in the column. There is no hidden whole-event reorder on a first drag: both modes post the
  column, so a drag moves one player and nothing else. The dry run's first line says which mode the
  column is in, and the bar beside the table says *Seeds: tier order* or *Seeds: arranged by hand*.
  The push record in `state.json.pushes` gains `seed_order: tiers | arranged` and `order`, the player
  ids it sent in seed order. Premise 1's "within-tier order left as start.gg already has it" no longer
  holds; the crosses-tier flag still shows a move that passes a seed of another tier relative to
  start.gg's current order.
- **Nothing goes stale before the push, and what is posted is what was on screen.** The push
  fingerprint covers **start.gg's side only** (the phase's seed ids, current numbers and players): a
  change there since the dry run refuses the post (409 `stale`) and the page shows a fresh dry run.
  Noah's own inputs are sent by the page at the click: the column (`seeding`) and the dry run it shows
  (`proposed`, the [seed id, number] pairs). The server saves the column first (write rules below),
  plans from **the column sent** (so a tier changed in another window cannot change what is posted),
  and posts only when its plan equals `proposed`; otherwise 409 `not-as-shown` with its dry run, the
  page redraws from it, nothing is posted. An open dry run is redrawn in the page after every drag,
  tier edit, reset or adopted change (`pushPlan` over the dry run's start.gg seeds), so dragging is
  never paused. The confirm dialog is modal; the column and the dry run are read after it is accepted.
  The post returns start.gg's side as it now stands, so the panel stays and a re-push needs no new dry
  run. This revises "Push mechanics" above, where the post was refused if the tiers had changed since
  the dry run.
- **Write rules** (`lib/seeding.js`; auditor findings 5 and 6). Every change of the column from the
  page (a move, a reset, the post) goes through one serialized chain in the page, in order, and carries
  `base` (the `rev` it builds on), `client` (a random id per page load) and `seq` (its write number):
  - a write from the same page whose `seq` is not newer than the stored one is an overtaken copy and is
    ignored, so the page's last write wins even if requests arrive out of order (a move made while the
    post is on its way is sent after it, and is what a reload shows);
  - a write whose `base` is not the stored `rev`, when another page made that change, is refused (409
    `seed-conflict`, with the current state): a stale window or a second one can never erase an
    arrangement made elsewhere, by a reset or by a tier-order post. The page then shows that order,
    drops its queued writes, and says nothing of its own was saved; Noah checks and posts again;
  - a write without `base` (scripts, tests) is not conflict-checked;
  - in tier order the column is posted as sent but not stored as an arrangement (`order` stays null),
    so later tier edits keep moving seeds; the push record keeps the order that was sent.
- **Exports.** The CSV export's Seed column (and `seeds.csv`'s `proposed_seed`) is the Seed column:
  the page sends the event it shows (`event`) and the column as it stands (`seeding`) in the export's
  POST body (main moved the export to a POST); without them, the tab's first event's saved state. The
  table's sort no longer renumbers a tab's export (it did in pass 1 and before, within a tier); a
  run-shaped folder (the CLI view) keeps the old numbering. So the export, the column, the dry run and
  the post agree in both modes (`test/seed-order.test.js`, ruling (b)).
- **Interaction.** Each seeded row has a ⠿ handle. Pointer events, not HTML5 drag-and-drop: the desktop
  shell builds its window without `disable_drag_drop_handler()` (`src-tauri/src/main.rs`, the
  `WebviewWindowBuilder` call), so Tauri's own drag-drop handler is on, and Tauri 2 documents that call
  as required for HTML5 drag-and-drop on Windows (model knowledge, not verified against a run). Pointer
  events need no change to the shell and behave the same in the webview and a browser. A line marks where the row lands; the table scrolls near its edges; Esc
  cancels. Keyboard (the WAI-ARIA reorderable-list practice): with the handle focused, ↑ / ↓ move one
  row, Page Up / Page Down ten, Home / End to the first / last seed, focus stays on the moved row, and an
  assertive live region says "tag: seed n of N". Moves step over rows hidden by *Needs tier only*.
  Moving while the table is sorted by another column first returns it to seed order; *Sort by seed*
  and the Seed header (ascending) do the same. When a tab has several events, *Seeds for* picks which
  event the column numbers (remembered per browser).
